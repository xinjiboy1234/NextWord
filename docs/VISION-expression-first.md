## 1. 文档目的

本文回答三个问题：

1. 项目最初的 AI-native 愿景是什么？
2. 当前实现兑现了多少、漂移发生在哪？
3. 要回到愿景，具体的差距和修正路径是什么？

结论先行：**项目没有做错什么，而是把愿景里"给用户看的外壳"（等级、分数）当成了内核来建设，真正的内核（详细画像 → 交叉验证 → 定制内容 → 质变重规划）停留在占位符状态。** 好消息是地基大多留好了，补齐不需要推翻现有任何东西。

## 2. 最初愿景回顾

产品的核心设想（本文以此为对齐基准）：

1. **测评之后，Agent 组织评估**，产出用户弱点的**详细描述**：词汇散乱程度、哪些生活场景的词汇弱/强、造句能力、阅读能力、语法薄弱点等；
2. **多个 Agent 交叉验证**评估结论——不是一个 Agent 说了算；
3. 根据验证过的画像，Agent 调用丰富的 skill 和工具**定制学习内容**；
4. 当对当前状态的细腻洞察发现用户瓶颈的**性质**发生变化时，**重新制定计划和内容**（"质的变化"不是指水平跃迁，澄清见 §5.1）；
5. Agent **后台运行**，用户只需要跟着内容学习；
6. 成本可控：组织课程的 Agent 一天跑一次，查词类调用走缓存、费用可忽略；
7. **固定等级只是辅助、给用户看的；真正的核心是综合的、详细的描述与评价。**

### 2.1 产品目标澄清

- 最终目标是**练出能够表达的水平**——不是高考试成绩，也不是专业英语；
- 因此"场景"指**生活表达场景**（日常起居、出行、购物点餐、社交、描述经历、表达观点与情绪等），不是医疗/商务类专业领域；
- **碎片化的间隔接触足以让学习者被动记住较"难"的内容**——但这推导出的是一套**分层的难度策略**，而不是"全面放开难度"：
  - **背词（识别层）**：允许偶尔掺入超当前水平的难词——间隔接触本身就是难词的吸收通道，只要求认识；
  - **造句等产出任务**：只用符合当前水平的词——产出要求不追难；
  - **阅读**：难词难免出现，**查词（lookup）就是应对机制**，不需要为阅读材料过度控词；
  - **水平测评**：词池严格按难度控制，接触性难词不进入测评——保证定级结果不被污染；
- "蜂群"的确切含义是**多 Agent 交叉验证**（防单一 Agent 误判），而非大规模 Agent 编排。

## 3. 现状盘点：愿景兑现了多少

### 3.1 已建成且方向正确的资产

| 资产 | 位置 | 对愿景的价值 |
|---|---|---|
| Score 内核（三维 0–100、幂等写入、日快照） | `ScoreProfileService` / `ProfileScoreSnapshotWorker` | 规划器的目标函数与状态筛查的时间序列数据 |
| SM-2 + 个人词汇状态 | `Sm2Service` / `UserWordRelationship` | 输入层（背词）的成熟机制 |
| 造句工作室全链路（四维 LLM 评分 → 回写 Score） | `SentenceService` / `PracticeScoreWritebackService` | **愿景在局部的完整实现**，全系统该长的样子 |
| 工具注册表（7 个工具） | `/api/tools` | Agent function-calling 的现成接口 |
| 后台任务队列 | `BackgroundJobWorker` | 夜间规划 Agent 的天然宿主 |
| BYOK（用户自带 LLM key） | `UserLlmSettings` | 规划 Agent 的成本由用户自担，商业模式成立 |
| 文章 `TopicTag`、句子 Scene 概念 | `Article.cs:15` 等 | 场景标签的碎片起点 |

### 3.2 停留在占位/未接通状态的部分

- **评估报告**：模板 + 工具预取数据，LLM 结构化叙事未实现（见 next-steps.md）——愿景里"综合详细描述与评价"的载体，目前恰好是唯一没做的部分；
- **`ReadingAssistantAgent`**：硬编码 intent 分支（`ReadingAssistantAgent.cs`），前端未调用；
- **工具注册表**：7 个工具建成，但没有调用它们的 Agent 存在；
- **默认 Mock LLM**：未知词难度一律回退 Basic/A1，个性化在默认配置下不成立。

### 3.3 漂移的定位

漂移轨迹在 `DESIGN-ai-learning-architecture.md` §7.2 有记录："AI 判官 + 规则引擎 + CEFR 翻译官"的收紧原则本身没错（保证了可审计性），但执行时发生了价值倒挂：

- 本该是辅助的**等级/分数，建成了工程投入最深的部分**（完整迁移、幂等、快照、Worker 体系）；
- 本该是核心的**画像与规划，留成了模板和未用代码**。

一句话：**仪表盘造好了，司机没造。**

## 4. 用"表达能力"标尺重检现状：关键错位

### 4.1 测评：识别型为主，与产出目标错位最深

- 四步中三步是识别型（词汇选择、拼写、阅读选择）；唯一产出型的造句步用**词数启发式**打分（≥6 词→3.5 分，`AssessmentService.cs:335-341`）；
- 词汇题**全库随机抽 12 个、不分难度带**（`AssessmentService.cs:241-262`）；题目携带 `DifficultyLevel` 但评分时不用——抽到 C1 词答对 50% 与抽到 A1 词答对 50% 定级相同；
- **无任何自适应机制**（答对升难、答降易）：API 是整批出题、整批提交（`GET/POST /api/assessment/{id}/step/{step}`），结构上排除了逐题分支的可能；
- 阅读步随机抽文 + **硬编码理解题**：题目永远是同一道，正确答案永远是 index 0（`AssessmentService.cs:291-296`），与文章内容无实际关联；
- 当前种子库仅 6 个词（`SeedData.cs:48-53`），测评与日常学习共用同一个小池子。

以表达能力为目标，测评应该以自由写作 + 产出型任务为主，识别型仅作参考。现状相当于"用识字量推断说话能力"。

### 4.2 `overall = min()` 与目标有张力

最短板定级（`AssessmentScoringService.cs:72`）意味着词汇识别分低会拖低整体定级，哪怕表达能力不错。对"练表达"的目标，产出维度应权重更高，或设立独立的"表达力综合分"作为主叙事。

### 4.3 每日选词的难度策略不分层

`[score, score+12]` 难度带一刀切地套在所有学习场景上，与 §2.1 的分层难度策略不符：对**背词队列**它过度保守（应允许掺入少量超水平的"接触词"——间隔接触足以形成被动记忆），对**产出任务**它又只看难度不看效用（应优先选表达效用高的词：高频动词、连接词、场景核心短语、观点句型）。分层后：识别层"效用优先 + 偶尔探高"，产出层"水平带内效用优先"。

### 4.4 Score 画像更新路径断裂

`ApplyUpdateAsync` 写入点：测评完成、确认挑战通过、造句/自由表达练习回写（`AssessmentService.cs`、`ChallengeService.cs`、`PracticeScoreWritebackService.cs`，T-022 起练习评分小步回写 Writing 维）。日常背单词和阅读行为**不产生** Vocabulary/Reading 分——三维分数里仍有两维缺少日常数据源。

### 4.5 内容地基缺失（P0）

- 种子内容：6 词、10 句、21 文，无批量导入机制；
- **`Word` 实体无任何场景/领域字段**（`Word.cs`）——"场景 X 词汇弱"级别的画像连数据源都不存在；
- 文章 `TopicTag` 是自由文本、未成 taxonomy。

## 5. 目标架构（修正后的愿景）

```
信号采集（已有）
  造句四维分 · 拼写逐字母错误 · 阅读查词 · 词汇掌握状态 · 分数日快照
        │
        ▼
① Profiler Agent → WeaknessProfile（结构化 JSON，每条结论必须挂证据：log id、样本原句、时间窗口统计）
        │
        ▼
② Verifier Agent → 逐条调工具核查证据；不通过的条目标记「存疑」，不进入规划输入
        │
        ▼
③ Planner Agent → LearningPlan 实体（未来 N 日内容配比：攻哪个场景、配哪类文章、造句目标）
        │        （夜间运行，BackgroundJobWorker 新任务类型；一日一次，成本可忽略）
        ▼
每日内容来源切换：DailyWordSelectionService / 阅读推荐 优先执行 Plan
        │
        ▼
产出端证据回流：自由表达中目标词/句型的自发使用、错误模式收敛、四维分趋势
        │
        ▼
④ 指标筛查提示异常/平台期 → Agent 细读近期产出原文 → 判断瓶颈性质是否变化 → 重跑 ①–③
```

关键设计约束：

- **规则引擎仍然拥有分数权威**。交叉验证验证的是"解读与计划"，不是分数本身——与 Score 内核 v1 确立的原则兼容，AI 不改分；
- **生成者—验证者对抗结构**（最小可行 = 2 个 Agent），不做多 Agent 投票；分歧大的条目直接降级为"存疑"，比引入第三个仲裁者更简单；
- **画像条目必须带证据引用**，这让验证从"LLM 判断"退化为机械核查，是防幻觉的核心手段；
- 验证与规划只在日/周周期运行，成本可忽略；查词类高频调用继续走文章级缓存。

### 5.1 "洞察当前状态"与重新规划（对"质变"的澄清）

先澄清"质的变化"的真实含义：**不是指学习者靠积累入门内容发生水平跃迁**——一直学菜鸟的知识不可能学成专家，这不可能，也不该作为系统预期。它指的是：Agent 对当前状态做**细腻洞察**时，发现用户瓶颈的*性质*发生了变化（例如从"词汇量不足"转为"会词但组织不成句"，或从"语法错误多"转为"语法正确但表达单调"），从而需要重新制定内容。

因此洞察不能只看聚合指标，必须**贴近用户的真实产出"字里行间"地细读**。分数说"语法 4.5/5"，细读原文才发现破绽：

- **回避模式**：从不用从句、只会 and/but 连接——指标不差，能力范围实际在收缩；
- **中式搭配**：字面正确但不自然的组合（如 learn knowledge、big rain）；
- **安全词策略**：反复使用少数熟练词，新学内容从不进入产出；
- **模板化表达**：背诵句型堆砌，稍作变化就出错；
- **语域错位**：该正式的场合用口语、该口语的场合用书面语。

这类破绽无法从阈值规则得出，必须靠 Agent 直接阅读近期产出原文（造句 + 自由表达样本）。机制分工：

- **聚合指标只做筛查与提示**：四维分趋势、快照序列、掌握度分布、目标词/句型自发使用统计，发现异常波动或平台期时提示"该细看了"（数据均已在采集）；
- **实质判断由 Agent 细读产出原文完成**：瓶颈的性质是什么、是否已从上轮计划针对的问题转移到新的层面；
- **重新规划为事件驱动 + 定期兜底**（如每周例行一次），而非每日判断。

期望管理：进步是渐进的、有边界的。计划的演进方式是"剥洋葱"——每轮细读揭开当前层面的破绽并针对性调整内容，而不是跳到更高层级。

### 5.2 背词功能的重新定位

**保留，但从主循环降级为输入层。** 表达的前提是认识，SM-2 是建立被动词汇最高效的手段，且是代码库中最成熟的部分。改动三点：

1. **选词权上交规划器**：队列由本周要攻的场景和句型决定，用户知道每个词为什么而背；队列中允许规划器掺入少量超当前水平的"接触词"（只要求认识，永远不进入造句等产出任务和测评——见 §2.1 分层难度策略）；
2. **毕业标准从"认识"改为"能用"**，词的生命周期四阶段：
   `认识（看词知义）→ 回忆（看义想词）→ 造句使用（提示下产出）→ 自发使用（自由表达中主动用出）`
   SM-2 只管前两阶段调度；进入产出阶段后由规划器安排产出任务；自由表达中自发正确使用一次才真正毕业；
3. **"Remembered/Forgot"自评只影响 SM-2 排程**，不再参与掌握度与 Score 计算——掌握度只看产出端证据。

拼写听写对表达目标边际价值较低，降为可选强化项。

## 6. 落地路径（按优先级）

| # | 事项 | 说明 | 性质 |
|---|---|---|---|
| 1 | **内容建设** | 生活场景 taxonomy（10–20 个）+ Word 场景标注（LLM 批量，复用 ReAnnotation worker 模式）+ 扩充词库（标准 = 表达效用优先） | 所有后续工作的地基，P0 |
| 2 | **测评重构** | 产出型任务为主 + LLM 真实评分；识别型降级为参考；分块自适应（词汇步按难度带分支，用 `IntrinsicScore` 作题目难度参数）；阅读题改为由文章生成；测评词池严格按难度控制，背词队列中的"接触词"不进入测评 | 纠正入口定级误差 |
| 3 | **WeaknessProfile v1 + Verifier** | 评估报告从"模板文案"升级为"带证据的结构化画像"持久化 + 验证者核查 | 愿景的核心物 |
| 4 | **PlannerWorker + 内容来源切换** | 夜间规划任务 + `DailyWordSelectionService` 优先执行 Plan | 用户可感知的变化 |
| 5 | **瓶颈性质洞察 + 重规划触发** | 指标筛查（快照/产出日志）提示异常或平台期 → Agent 细读近期产出原文判断瓶颈性质（§5.1）→ 触发重规划 | 闭环 |

前两步是纯增量（新实体 + 新任务类型），不动现有闭环；第 4 步只改选词服务的数据来源。
